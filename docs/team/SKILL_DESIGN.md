## 1. 10 役割枠の分類

各職業に **必ず以下 10 枠を埋める**。職業性で枠の解釈は柔軟だが、機能多様性は守る。

| # | 役割 | 機能 | typical type | typical cost / CD |
|---|---|---|---|---|
| 1 | **基本攻撃** | 毎ターン使える主力。命中重視・cost 低 | attack | cost 1-3, CD 0 |
| 2 | **必殺技** | 職業の代名詞、ボス級にも通る | attack | cost 12-16, CD 3-4, power 22-26 |
| 3 | **自バフ** | 次撃強化 or 短期 stat up | buff (self) | cost 5-8, CD 2-3 |
| 4 | **敵デバフ** | 状態異常付与 / 弱点公開 / stat down | debuff (enemy) | cost 6-10, CD 2-3 |
| 5 | **仲間援護** | heal / 状態解除 / 蘇生 (戦士系は「応急手当」で職業性維持) | heal (ally) | cost 8-14, CD 3 |
| 6 | **AOE** | 全敵対応 | attack (all_enemies) | cost 11-14, CD 3-4, power 12-16 |
| 7 | **持続バフ** | 3-5 ターンの長 buff (パッシブ風) | buff (self / all_allies) | cost 10-12, CD 4-5 |
| 8 | **連携** | 直前 type と異なれば +bonus (C30 chain combo) | attack | cost 8-10, CD 2 |
| 9 | **究極 (ultimate)** | power 最大、cost 最大、CD 最長、boss 戦の決め手 | attack | cost 25-30, CD 7-8, power 45-55 |
| 10 | **signature** | 職業の象徴、唯一性ある効果 | special / buff | cost 10-15, CD 5 |

### 役割の柔軟性

- 戦士系で「heal」枠が違和感あれば「冷徹な見立て (応急手当)」のように職業性で再解釈
- 魔導師系で「基本攻撃」枠が物理だと違和感あれば「魔力放出」のような魔法系に
- 神官系の「究極」は不死特攻の超大ダメージ
- 盗賊系の「signature」は「影分身」のような敵狙い回避

職業性が前面に出るなら、type / element / power の数値は方針内で自由。

## 2. 命名規則

### 命名のフォーマット

**[quirk] × [機能]** または **[漢字熟語] × [読み]**

例:
- 眼鏡 × meteor = 「眼鏡メテオ」
- 観察 × 一撃 = 「観察打ち」
- 鎮魂 × 歌 = 「鎮魂歌」

### 文字数

- 4-8 字程度 (HUD 表示で詰まらない長さ)
- 漢字主体、和風寄り
- カタカナ混在 OK (技名感)

### 避ける命名

- 「攻撃 1」「強攻撃」のような番号 / 機能直書き
- 英単語そのまま (「Slash」「Heal」)
- 長すぎる名前 (10 字超)

---

## 3. description (説明文) の指針

### 文字数: 50-80 字目安

短すぎ: 機能だけ → 職業性が出ない
長すぎ: 読まれない

### 含めるべき要素

1. **動作の描写** — 「眼鏡越しに敵の動きを見据える」
2. **機能** — 「クリティカル率 +50%」
3. **職業性のフレーバー** — 「眼鏡戦士の代名詞」「戦術手帳を開く」など

### 例 (眼鏡戦士の「分析の構え」)

> 戦術手帳を開き敵の癖を読み解く。次の通常攻撃のクリティカル率 +50%。

3 要素揃っている: 動作 (戦術手帳を開く) + フレーバー (癖を読み解く) + 機能 (クリ率 +50%)。

## 4. 職業性の出し方

### 4.1 quirk × 役割 のマッピング

職業の quirk (1 単語フック) を 10 役割それぞれに反映。

例: **眼鏡戦士 (quirk = "眼鏡")**

| 役割 | quirk 反映 |
|---|---|
| 基本攻撃 | 観察打ち (見据える) |
| 必殺技 | 眼鏡メテオ (レンズで陽光集める) |
| 自バフ | 分析の構え (戦術手帳) |
| 敵デバフ | 観察眼 (弱点公開) |
| 仲間援護 | 冷徹な見立て (応急手当を観察知識で) |
| AOE | 閃光乱反射 (眼鏡を眩ませる) |
| 持続バフ | 観察の習慣 (周囲を観察し続ける) |
| 連携 | 予測射撃 (味方の動きから敵を読む) |
| 究極 | 終局視 (運命を眼鏡越しに見切る) |
| signature | 眼鏡反射 (1 ターン物理 50% 反射) |

10 枠中 9 枠で「眼鏡 / 観察 / 分析 / 読み」が反映。職業性がブレない。

### 4.2 element の選択

quirk に応じた element 選択:

| quirk 系統 | typical element |
|---|---|
| 火・炎 | fire |
| 水・氷・雪 | water |
| 風・空 | wind |
| 大地・石 | earth |
| 光・聖 | light |
| 闇・呪 | dark |
| 中立・物理 | null |

例:
- 眼鏡戦士: 主に null (物理) + light (眼鏡メテオ・閃光乱反射) + dark (終局視)
- 雪国戦士: water 寄り
- 古竜の血を引く者: fire / dark
- 妖精郷育ちの魔法使い: wind / light

### 4.3 baseStats との整合

10 スキル運用には MP プールが必要。baseStats.mp は **最低 16** を目安に。
攻撃職 (warrior/rogue) で mp が低い場合は、必殺技 + 究極 + AOE + 反射 の cost 合計を 60 程度に抑える。

## 5. バランス指針

### 5.1 power / cost の関係

`power × (target 数) ÷ cost ÷ (CD + 1)` を **dpc (damage per cost / cooldown)** として、
役割枠ごとに目安:

| 役割 | dpc 目安 |
|---|---|
| 基本攻撃 | 高 (5-8) |
| 必殺技 | 中 (4-6) |
| AOE (全敵) | 中 (4-6 × 敵数) |
| 究極 | 低 (2-3、爆発力で勝負) |
| 連携 | 中 (4-6、ボーナス込み) |

### 5.2 役割枠の cost 制約

| 役割 | cost 上限 |
|---|---|
| 基本攻撃 | 3 |
| 自バフ / 敵デバフ | 10 |
| 仲間援護 | 14 |
| AOE | 14 |
| 必殺技 | 16 |
| 持続バフ | 12 |
| 連携 | 10 |
| 究極 | 30 |
| signature | 15 |

### 5.3 CD の制約

- CD 0: 基本攻撃のみ
- CD 2-3: 自バフ / 敵デバフ / 連携 / AOE / 仲間援護
- CD 4-5: 必殺技 / 持続バフ / signature
- CD 7-8: 究極

→ 1 戦闘 (3-5 ターン) 中に 必殺技 1-2 回 + 究極 0-1 回 + 通常スキル数発 が想定発動回数。

| 44 | mage 13 職 | 130 |

| 46 | cleric 12 職 | 120 |
| 47 | craft 13 職 | 130 |
| 48 | support 12 職 | 120 |
| 49 | heretic 12 職 | 120 |
| 50 | rare 12 職 | 120 |
| **合計** | **100 職** | **1,000 スキル** |

その後、procedural 1720 職を curated 化:
- +200 サイクル目安 (1 セッションで 5-10 職)
- 数ヶ月計画

### 各サイクルの作業フロー

1. 該当カテゴリの全職リスト確認 (`prisma/curatedJobs.ts` の category 別)
2. 各職の quirk / signatureBio を再確認
3. 10 役割枠を quirk × 役割で命名 (この設計指針 §4.1 の要領)
4. 役割枠ごとに type / element / power / cost / CD を §5 の制約内で決定
5. description を 50-80 字で書く (§3)
6. `uniqueSkills` 配列を 1 → 10 に拡張
7. `npm run seed` で投入確認
8. `npx tsc --noEmit` / `npm run lint` で検証
9. CLAUDE.md §10.5 の報告フォーマットでコミット

## 8. 既存 procedural skill 5039 の処遇

**方針**: Phase 1 (Cycle 40) で procedural job 1720 を non-curated 扱いで 一旦封印 (`Job.curated = false` の job を表示しない)。同時に procedural skill も seed から外す。

Phase 2 完了後、procedural job を curated 化する際に skill も再設計。

これにより:
- DB 上に「機能はあるが識別性ゼロ」の skill が残らない
- プレイヤーが見るスキルは全て手作りの一品
